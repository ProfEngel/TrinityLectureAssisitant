# Trinity v0.16.59 – Canvas-Start unter Windows stabilisiert

## Behoben

- Der Canvas-Produktionsserver löst Webbuild und Standard-Datenordner relativ
  zu seiner eigenen Installation auf. Ein absoluter Start aus einem anderen
  Arbeitsverzeichnis liefert deshalb weiterhin die Canvas-Weboberfläche statt
  `Cannot GET /`.
- Ein fehlender Webbuild erscheint als verständliche Wartungsseite. Unbekannte
  API-Routen liefern eine klare JSON-404-Antwort.
- Der Health-Endpunkt meldet mit `uiReady`, ob Dienst und Weboberfläche
  gemeinsam einsatzbereit sind.

## Diagnose und Oberflächen

- `trinity canvas status` unterscheidet bereite, gestoppte, fehlende,
  ungebaute und nur teilweise erreichbare Canvas-Zustände.
- `trinity doctor` nimmt Canvas in die Systemprüfung auf.
- Der Desktop-Reiter zeigt bei Nichterreichbarkeit eine Trinity-Fehlerseite
  statt einer technischen Browsermeldung.
- Desktop-Control und das authentifizierte Companion-Dashboard erhalten
  denselben Zustand samt der von Trinity verwalteten Canvas-Adresse.

## Installation

- Das Windows-ZIP-Fallback lädt genau den von Trinity geprüften
  Canvas-Commit `21099e2d17181be2d3e0ad62210abfe1fda87cf8`.
- Git-Installationen verwenden denselben Stand über das
  `components/TrinityCanvas`-Submodule.

## Prüfung

- 238 Trinity-Tests unter Python 3.13
- Python-Compile-Checks
- Canvas-Lint und Typecheck
- Canvas-Produktionsbuild
- Produktions-Smoke-Test aus einem fremden Arbeitsverzeichnis
- verwalteter Canvas-Start, Root-GET HTTP 200, Health und Stop auf macOS
- macOS-/Windows-CI um Canvas-Build und Produktions-Smoke erweitert

Vault-Inhalte, Profile, Sessions, Memory, RAG-Quellen, Soul und
Benutzerkonfiguration werden durch dieses Update nicht verändert.
